## 1. 产品目标与交付边界

GitFinder 是开发者本机上的项目、Git 仓库与部署关系中心。近期交付目标是“离线可靠、可解释、可恢复、可维护”的桌面版本；中期增加有证据的开发—构建—部署事件链；Web 与云同步作为独立、可选的后续能力。

典型闭环：发现项目 → 查看 Git 与部署关联 → 在白板整理关系与备注 → 修改、保存、关闭、重新打开 → 根据事实定位故障和本地代码。文件操作、Git 写入和目录授权必须经现有受控入口；Coolify 仍只读，不新增停止、重启、部署或服务器配置写入。

## 3. 目标架构与代码定位

保持“原生JS应用壳 + React Flow白板岛”，不因为使用React就重写整个应用。参见 [ARCHITECTURE.md](../../ARCHITECTURE.md)；下表是当前接续定位补充。

| 层 | 现有入口 | 修改规则 |
| --- | --- | --- |
| 组合根/权限 | `main.js`、`preload.js`、`src/main/ipc/security.js` | UI只经受信IPC；新能力显式验证参数、目录和调用页 |
| 本地事实 | `localProjectService.js`、`gitService.js`、`fileOperationService.js` | 不以目录显示名代替稳定ID，不对用户目录跑破坏性测试 |
| 部署事实 | `coolifyProviderService.js`、`endpointHealthService.js`、`remotePanelObservationService.js` | 数据源、时间、新鲜度分离；失败不清空有效缓存 |
| 白板持久化 | `relationshipBoardPersistence.js`、`whiteboardDocumentService.js`、`whiteboardPackageService.js` | 自动/手动保存同队列，旧结果不能覆盖新编辑，取消/失败可恢复 |
| 模型与结构 | `relationshipGraphModel.js`、`relationshipProjectStructure.js` | schema兼容、成员权威不变，禁止保存React Flow内部对象 |
| 几何与显示 | `relationshipLayoutPrimitives.js`、`panelTopologyProjection.js`、`relationshipFlowAdapter.js` | 算法、Controller、实际Flow显示三层都测；布局不改groupId |
| UI编排 | `relationshipBoardController.js`、`relationshipBoardActionRouter.js`、`nativePanelController.js` | 拆分职责保持旧入口，不同时重写路由和存储 |
| 账号与更新 | `accountService.js`、`accountStore.js`、`updateService.js` | 账号/第三方Token隔离；检查、下载、安装分别获用户确认 |
| 工程接续 | `management/development-tasks.json`、`scripts/handoff-status.js` | 单一任务源，生成视图不反向改任务，不自动判定通过 |

上述服务默认位于 `src/main/services/`，白板Controller位于 `src/renderer/scripts/`，纯函数位于 `src/shared/`；任务卡提供可直接跳转的完整路径。

### 数据流与权威

文件/Git/Coolify → 主进程校验与受控服务 → 最小IPC结果 → 领域投影 → 显示几何 → React Flow。保存走相反的表示转换，但只写领域数据，不把缓存或观察状态升级成权威事实。应用用户数据、白板项目、代码仓库和发布制品分别管理。

本轮不引入SQLite。现有存储格式先完成盘点与兼容验证，之后是否迁移要有新ADR、恢复方案和用户确认。`management/` 是本仓库的开发事实源。用户已要求通过GF-PROGRESS-001打通开发任务/仪表盘：App直接读取仓库台账并生成内存只读投影，保留没有台账项目的Local Project Manager兼容入口，不修改外部连接器或另起同义任务库。实现与验收见[连接说明](REPOSITORY_PROGRESS_BRIDGE.md)。

## 5. 近期详细工作包

### 5.1 GF-QUALITY-001：可重复场景与规模基线（建议下一开发任务）

第一步把现有布局/保存/媒体验收需要的fixture建立过程做成可重复、隔离的准备步骤，明确使用独立profile与固定输出目录。现有验证脚本并不自动生成所有fixture，不能让接手者猜测格式或复制真实用户配置。

以35个部署的已记录案例为基线（部署数不等于总实体或显示节点数），再生成100、300、1000节点的确定性样本，涵盖主机数量不均衡、单/多访问点、手动/锁定组、隐藏层级、独立文档与本机工作区。分别记录首屏、重排、拖动、缩放、保存、重开耗时和节点计数。性能预算在取得硬件/数据基线后确定，不以“看起来流畅”或固定测试数作为完成条件。

验收必须覆盖相同输入重复布局不漂移、后台刷新不复位、真实Flow模型不强制改单列、事实及成员归属不变、重开后布局一致。失败截图、几何差异和计时均保存为可重现证据。

### 5.2 GF-UI-001：输入、全屏和可访问性

沿用alpha190未确认的指针偏差记录，在实际Electron中采集pointer序列、缩放、DPR、窗口/全屏边界、菜单开关及blur/cancel。覆盖桌面/窄屏、浅/深主题、减少动画、键盘访问以及菜单不穿透。辅助功能权限拒绝要写明，不把CDP鼠标当macOS系统鼠标。只在复现并定位后修产品代码；未复现也要保留测试条件和未证实原因。

### 5.3 GF-DATA-001/002：保存、媒体与恢复

在临时目录测试写入失败、旧revision、进程中断、外部删除/移动、损坏JSON/包、同名附件和被拒绝的外部引用。确认保存结果不会覆盖新编辑，错误后原内容仍可见，取消另存为不丢失待保存修改，独立白板不意外写本机合集。

真实项目目录中的图像更换、撤销/重做、旧路径恢复、迟到预览、缺失附件、便携包搬迁要同时核对源路径、文件字节、界面内容和版本。受控失败注入与真实IO检查分别记录；不删除用户附件来模拟故障，不自动清理可能供撤销使用的历史资源。

### 5.4 GF-ARCH-001 / GF-PERF-001：拆分与定点优化

先标注Controller中纯几何、显示派生、持久化调度、菜单生命周期的输入输出。保存已抽取，不再重做。下一个独立模块优先选择无UI副作用的显示几何或菜单状态，保留旧方法委托以便逐步迁移。新增模块必须更新正式HTML和旧fixture装配顺序。

对确认的热点再采用索引、增量更新、同帧合并或请求取消。缓存键应包含来源/版本/显示配置；迟到结果不能覆盖新源，卸载要清理监听和帧请求。报告必须给出前后相同工作负载，区分调用次数、文件写入次数、耗时与实际帧率，不用代码行数充当性能证明。

### 5.5 GF-STORAGE-001：当前数据格式盘点，非迁移

从服务与测试核实每种已实现文件的所有者、默认路径、schema、大小上限、原子写、备份、版本冲突和跨平台路径规则。项目ID、目录授权、Token、白板布局、部署缓存不可混表。现有未提交存储设计留在用户工作树，未获授权不并入；清单中的“已实现格式”和“未来目标格式”必须分栏。只有GF-DB-001另行获准才进入迁移。

### 5.6 GF-RESOURCE-001：资源组合入口一致性（alpha.197已交付）

主机及云Project按真实来源/主机作用域组合，部署带端点，端点不反向扩散；资源库加号、拖放和补全共用原子流程。混合/独立白板复用主机容器，持久层只保存领域实体/关系，不保存显示层host-bubble对象。旧实时锚点与完整离线快照分开识别，不能按source=observed一概判断。现有位置、备注、手工归属和容量失败原子性保持回归。实现与安装证据见[RESOURCE_CONTAINERS_ALPHA197.md](RESOURCE_CONTAINERS_ALPHA197.md)；规模/全布局组合仍属于GF-QUALITY-001，不凭本轮通过宣称全场景覆盖。

## 6. 可分发工作包

GF-CI-001核查当前远端CI，旧失败诊断不代表今天仍失败；修复要区分Linux、macOS、Windows结果。配置存在不等于各平台通过。

GF-WIN-001在真实Windows x64普通路径构建并安装NSIS，默认GPU启动、基础交互、更新/卸载与用户数据保护分别记录。不能只用`--disable-gpu`证明可发布。

GF-UPDATE-001先在隔离发布源测错误版本、校验失败、断网/取消、下载进度与明确重启；正式Developer ID签名/公证和Windows签名必须另有证据。GF-RELEASE-001在获得公开发布授权后才上传产物，先确保产物可读再原子切manifest，验证网站、清单、客户端版本和回滚方式一致。

GF-AUTH-001只补现有Casdoor/OIDC真实账号流程验收，不新建第二个账号体系，不索取或提交真实密码。未登录仍能使用本地核心功能。用户账号输入与生产配置要另行确认。

## 7. 全流程事件工作包

依据 [通知与全流程方案](../product/delivery-observability-notifications-plan.md)。现有Provider已读取部署状态/部分历史信息；缺口是完整的本地事件模型、增量持久化/去重和可追溯时间线，不重复建立Provider。

GF-EVENT-001先定义最小事件身份：provider、资源/部署ID、事件类型、来源、源时间/接收时间、结果、提交证据。未知身份保留为未关联事件，禁止按名称猜测。API是否支持有界分页及具体字段必须在实施时核验实际版本，不能照旧文档假定。

GF-EVENT-002实现一仓库对应测试/生产两个部署的多次记录，刷新/重开不重复，失败提交不冒充运行版本；点击可定位白板和本地仓库。

GF-NOTIFY-001实现故障周期、冷却、恢复和免打扰；明确部署失败与HTTP瞬态阈值不同，应用退出不承诺弹窗。GF-WEBHOOK-001默认暂缓，只能先用本地模拟服务测来源认证、体积限制、重放、乱序和游标；生产接收器、凭据与通知配置须明确授权。GF-CI-EVENT-001只选一种用户实际CI源，关联提交/构建/制品/部署，不从时间先后直接推断因果。

## 8. Web、云同步与数据库决策关口

遵守 [Web与发布备忘](../product/web-cloud-release-memo.md) 和 [云同步边界](../product/cloud-whiteboard-sync.md)。`server.js`仍是本机工具服务，不可直接当公网多租户后端。

GF-DB-001保持暂缓。任何JSON到数据库迁移必须有唯一事实源、备份、幂等迁移、失败回滚、旧版读取策略和真实跨平台验证；数据库选型不是这次方案文档隐含的执行许可。

## 9. 安全、兼容与回退

- 不把用户文件、缓存原始响应、账号或凭据复制进仓库；只使用脱敏样本，日志白名单输出。
- 测试路径必须可证明位于独立profile/临时目录；未知profile或调试端口进程不匹配立即停止。
- 多AI共同工作先记录HEAD和原dirty路径；不`git add .`、不强制reset、不开第二个竞争安装进程。
- 大版本迁移、服务端部署、正式发布需要明确授权；本机默认交付按AGENTS执行。
- 应用备份、数据备份、Git回滚是三种不同恢复手段。恢复旧App不能自动恢复新格式数据；出现非预期数据差异先保留两份证据，不覆盖用户新编辑。

## 11. 执行与完成定义

一个工作包至少产出：明确任务编号与范围、失败用例/测量、最小实现、专项与全量结果、安装交互证据、已知限制、版本/提交/恢复路径。`delivered`仅表示任务声明范围内已交付，用户确认由独立字段记录；计划、测试通过、安装通过、推送和正式发行不得互相替代。

### 管理入口与系统浏览器边界（GF-COOLIFY-LINK-001）

用户确认管理后台链接由系统默认浏览器打开；不硬编码浏览器、不默认嵌入第三方后台。来源身份、网站访问、管理地址和登录权限分别处理；白板便携文件不含凭据或受信后台URL。alpha198已交付，证据与数据校验限定见[COOLIFY_CARD_LINKS_ALPHA198.md](COOLIFY_CARD_LINKS_ALPHA198.md)。

### GF-CONTAINER-LIFECYCLE-001 · 已交付的生命周期约束

alpha199统一来源Project在线/离线操作身份，隐藏、显示层开关与存储完整性分离；独立保存保留隐藏字段和已保存的不可见层成员。不能把可见投影当作全部持久内容，也不能因runtime被剥离就把来源容器变成手工群组。详见[验证与交付](CONTAINER_LIFECYCLE_ALPHA199.md)。
