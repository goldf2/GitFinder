# 进度维护与人员/AI接续协议

## 1. 单一事实源

任务事实只写入 `management/development-tasks.json`；`PROGRESS.md`由脚本生成。当前版本和环境只在 `CURRENT_STATE.md` 顶部有效块维护；`NEXT_ACTIONS.md`解释任务源中的唯一下一任务。旧历史区和 `docs/ai-handoff/` 不能反向覆盖这些记录。

用户已要求打通App：GF-PROGRESS-001将仓库台账直接适配为开发任务与仪表盘的只读投影，保留Local Project Manager兼容源。任务事实仍只改项目内台账，不生成第二套可编辑CSV；实际实现/验收状态见REPOSITORY_PROGRESS_BRIDGE.md。

## 2. 状态定义

| 状态 | 使用条件 | 必填补充 |
| --- | --- | --- |
| planned / 计划中 | 已分解但还没开始，依赖或范围待落实 | 明确下一动作、验收与来源文件 |
| ready / 可开始 | 依赖已交付，无未决执行授权 | 建议角色，执行前认领 |
| in_progress / 开发中 | 当前执行者已认领并开始真实工作 | 非unassigned负责人、接续点 |
| blocked / 阻塞 | 正在需要的输入、资源或授权无法继续 | blocker说明缺什么、由谁确认、恢复动作 |
| verified / 已验证 | 范围内实现和源码/专项已验证，尚未完成交付 | 指向真实验证记录；不得假写安装或推送 |
| delivered / 已交付 | 任务定义的交付门槛完成 | evidence、版本、完整源码commit；用户反馈单独记录 |
| deferred / 暂缓 | 显式范围外或等待新的产品决定 | 暂缓原因和重新启动条件 |

用户验收字段：`pending`、`confirmed`、`not_required`。历史安装验收通过不等于用户已确认；只有明确用户反馈才能改为confirmed。负责人是协作角色或实际执行者，不虚构团队成员；未认领填写unassigned。

状态只能由执行者根据证据编辑，脚本不自动升状态。建议流转planned→ready→in_progress→verified→delivered；阻塞/暂缓保留原证据，修复后再恢复。重开已交付任务要记录新问题或建立后继任务，不抹去既有交付。

## 3. 何时必须更新

开始一项任务前：核对HEAD、dirty、任务依赖，填写owner和in_progress。得到一次专项/全量/安装结果后：立即写真实命令、退出状态、数量和证据路径，并更新任务记录时间。发生用户范围变更、失败、阻塞、提交、构建、安装或推送时：在继续大段工作前更新接续点。

准备中断、切换人/AI、结束本轮答复前：替换CURRENT_STATE有效块、NEXT_ACTIONS有效块，追加SESSION_LOG，执行 `npm run handoff:update && npm run check:handoff`。下轮先读这些记录，不依赖聊天记忆。

该要求是事件驱动的工作纪律与提交检查，不是定时后台任务。`handoff:update`只生成阅读视图；没有任何脚本会自动开发、自动运行全部测试或证明人工作业已完成。

## 4. 证据要求

任务`evidence`使用仓库内可获取的文档路径，交付记录再链接本机原始日志。完成证据要包含实际工作版本、命令与结果、范围、平台、安装/交互、恢复和未验证项。源代码文件或测试文件存在只能证明实现/用例存在，不能单独证明运行通过。

原始日志优先写 `dist/<task-evidence>/`，不提交敏感数据和大制品。换机原始日志不可见时，仓库里的摘要是“历史证据”，必要时复跑。实际修改过的用户数据要做结构或哈希对比；不一致时明确哪些字段改变，不一律写“完全没变化”。

`npm run check:handoff`检查字段、日期、任务ID、依赖环、依赖状态、路径、已交付元数据、主入口链接及生成视图是否一致。它不会验证远端是否真的推送、日志是否真实、截图是否正确、Markdown锚点或全部历史链接，也不会替代运行测试和人工审阅。

## 5. 多人/多AI协作与防覆盖

1. 每名执行者使用独立worktree/分支，领取不同任务；不覆盖别人的in_progress owner。集成人负责版本号、文档有效块、安装和推送，其他任务先交付可验证提交。
2. 同一主机只允许一个安装负责人。发现版本、HEAD或文件哈希在工作期间变化，先检查diff再合并，不能盲目继续覆盖。
3. 只暂存本次路径或hunk。共享文档已有未提交内容时，分离本轮增量；不把本机未提交设计草稿当远端已发布资料。
4. 跨任务消息按来源/目标/摘要记录一次成功交接，不因恢复或超时重复发送；AgentDock任务记录辅助执行，项目文件才是跨工具的接续依据。

## 6. 交接卡模板

复制到SESSION_LOG的新条目，必要时新建对应验收记录：

```text
时间（含时区）/ 任务ID / 执行者：
用户目标与本轮范围：
基线版本、HEAD、原有未提交路径：
实际完成及修改文件：
验证命令、平台、通过/失败数量、证据路径：
源码commit / 构建commit / 安装版本 / 推送commit：
数据保护和可恢复备份：
失败、未验证、已排除的假设：
阻塞条件与所需决定（没有则写无）：
唯一下一任务与第一条可执行动作：
```

## 7. 不同中断点如何接续

| 停止点 | 恢复动作 |
| --- | --- |
| 改了一半未验证 | 读取diff和失败用例，保持in_progress，不打包或宣称修复 |
| 源码通过但未安装 | 确认构建commit，完成可追溯包和安装专项后才交付 |
| 安装失败 | 保留失败日志和旧App，不推送失败版本；先恢复可用应用 |
| 安装通过但推送失败 | 保留本地提交，确认远端后普通push，不强推；状态保留verified并写阻塞 |
| 推送成功但记录未收口 | 核对ls-remote，再提交记录增量；运行包绑定原源码commit，不伪造重新构建 |
| 用户正在编辑真实白板 | 不运行真实配置的写测试，不覆盖新内容；用独立profile验证 |

## 8. 收口检查

确认验收没有把fixture成功等同于实机成功；确认版本与锁文件一致、制品绑定源码、旧App可恢复；确认原dirty内容保留和实际数据边界；确认CURRENT_STATE、nextTaskId、PROGRESS和发布记录一致。用户确认某个修复有效后，再按根规则将修复报告归档到支持文档；未确认不得代签。
