# GitFinder 2：全流程可视化与 Coolify 通知集成开发方案

日期：2026-08-31
状态：主开发任务已于 2026-08-31 接收并衔接现有工作；M1 为后续优先垂直切片，尚未实施。本文不代表通知功能已交付或生产配置已完成。

## 1. 用户目标与本次边界

GitFinder 应串联“本地开发 → Git 提交 → 测试/构建 → 部署发布 → 线上运行 → 访问检测 → 问题返回本地代码”，提供统一的资源关系图和过程追溯。

本轮优先补齐 Coolify 部署历史、运行事件和通知：API 获取事实，Webhook 提供及时事件；不重新实现部署平台，不依赖 Xiangshu Panel。保留现有本地项目、仓库、白板和直接 Coolify 连接。

本次交接只新增此方案并发送主任务；不授权立即部署接收服务、修改生产通知设置、创建凭据或扩展服务器访问范围。主任务应在当前工作的安全检查点接续，不丢弃正在进行的工作。

## 2. API、Token 与推送的区别

- **API** 是程序交互接口，不是凭证。
- **API Token** 是调用接口的访问凭证；已有只读 Token 不等于已订阅通知。
- **当前拉取路径**：GitFinder 主动请求 Coolify API，Coolify 返回状态或部署记录。
- **通知推送路径**：Coolify 发生事件后，向另行配置的 Webhook 接收地址发送 HTTP POST。
- **桌面订阅路径**：GitFinder 主动连接通知接收服务，通过 SSE 等机制接收事件。该能力由本方案实现，不能假设 Coolify 已提供可直接订阅的 SSE 接口。

Coolify 官方已公开通知 Webhook 配置与事件载荷；正式接入前应核验用户实际 Coolify 版本支持的事件、字段和鉴权方式。

参考：[通知配置](https://coolify.io/docs/knowledge-base/notifications/#webhook)、[事件载荷](https://coolify.io/docs/knowledge-base/webhook-payloads)。

## 4. 目标架构

### 4.1 必选基础：直接 API 拉取

GitFinder 使用现有应用自有会话直接读取 Coolify；复用当前轮询与并发控制。先显示本地白板，再异步刷新远端数据。请求失败不应清空白板、重排卡片或将“数据源失联”伪装为“所有服务停止”。

启动、手动刷新、定期刷新和收到事件后均可校准相关资源。轮询只能恢复 API 保留的事实或历史，不能保证补回停机期间发生又恢复且未被记录的短暂异常。

### 4.2 可选增强：常在线通知接收服务

推荐路径：Coolify → HTTPS Webhook 接收服务 → 持久事件记录 → GitFinder 主动订阅。

- 桌面通常没有固定、持续可达的接收地址；不默认给用户电脑开放入站端口或创建隧道。
- 接收服务只负责验证来源、过滤字段、保存、去重和转发事件，不需要 Coolify 管理 API Token，也不复制 Panel。
- 第一版选择 SSE 与游标补取即可，不同时实现 SSE、WebSocket 等多套协议。
- GitFinder 未连接时保存事件；重连后按游标补取。补取内容取决于明确的保留策略，不能承诺无限历史。
- 未配置推送时，直接 API 和白板功能照常使用。
- 接收服务的地址、部署位置、访问控制与保留策略由主任务提出，取得用户确认后才实施生产部署。

## 5. 数据与状态语义

### 5.1 事件最小信息

建议保留本地事件 ID、实例 ID、事件类型、可用的资源/部署 ID、结果或严重程度、简短摘要、来源、源事件时间（若存在）和接收时间。按白板已有关系解析项目、仓库和本地路径，不在 Webhook 中传递本机路径。

- 实例身份来自已配置的接收通道/会话，不能仅相信载荷自报的实例名。
- 官方部署事件可带 `application_uuid`、`deployment_uuid`；服务器事件可带 `server_uuid`。不同事件字段不齐，缺失时保留“未关联事件”，不按名称擅自绑定。
- 源消息没有发生时间时记录接收时间，并标明语义，不能冒充精确故障时间。
- 显示别名不改变资源身份。

### 5.2 去重、乱序与故障周期

- 有稳定源事件 ID 时优先使用；部署事件可按实例、部署 ID、事件类型确定重复。
- 运行状态变化按“单次故障周期”去重；恢复后再次故障必须生成新事件，不能永久按资源和类型去重。
- 推送和轮询命中同一次部署/故障时合并关联，不重复通知。
- 迟到的失败事件保留为历史，不直接覆盖较新的健康状态；收到事件后刷新 API 能验证的事实，不能验证的标注来源与待核实状态。

### 5.3 必须分开的四种状态

1. 当前运行状态。
2. 最近一次部署结果。
3. 访问点实际检测结果。
4. 数据源同步状态和观测时间。

“当前运行正常，但最新部署失败”是合法状态。配置中的提交、最新失败部署的 SHA、最后一次成功部署 SHA 均不能无条件等同于当前运行容器的版本。缺少可验证的运行版本证据时明确显示未知。

## 6. 分阶段垂直切片

### M1：部署历史与项目事件列表（优先，可不部署服务）

- 使用实际版本支持的只读 API 分页读取应用部署记录，替代只取一条；设置合理数量上限，不无界抓取。
- 将部署 ID、状态、提交、时间与现有实例/资源身份关联，提供增量事件记录。
- 在项目详情或可折叠事件组件展示记录，支持按资源、事件类型和未处理状态筛选，不新增强制一级主视图。
- 从事件定位白板卡片、关联仓库与本地目录；没有本地副本时保留事件并明确提示。

**验收：** 一个仓库对应测试/生产两个部署，能分别查看部署记录与提交；失败部署不被标成当前运行版本；刷新与重启不会重复生成同一部署事件。

### M2：桌面通知与白板联动

- 在主进程实现原生系统通知；桌面运行或已实现的托盘驻留期间可通知，普通应用退出/休眠时不承诺桌面弹窗。
- 明确的部署失败可立即通知；本机 HTTP 探测的短暂异常采用连续失败阈值，不能机械要求同一条部署失败消息重复 2–3 次。
- 故障周期去重、冷却、恢复通知；提供必要的项目/环境/严重程度筛选及免打扰规则。
- 点击通知定位对应资源/项目；用户主动选择后才打开 Coolify 或本地目录。
- 卡片区分当前状态、最近发布失败和未读事件，不覆盖用户名称、备注和布局。

**验收：** 同一事件重复读取只通知一次；恢复及下一轮故障分别可通知；重启、免打扰、资源已删除、通知权限拒绝都有明确且可恢复的行为。

### M3：Webhook 接收与实时订阅（部署前需用户确认）

- 先使用本地隔离接收服务和模拟事件完成协议、存储、鉴权、订阅与重连测试。
- 初期支持部署成功/失败、应用/容器意外停止、服务器失联/恢复；其他官方事件先保持可识别的通用记录，避免一次实现全部运维模块。
- 来源鉴权通过后才入库；事件持久化成功后再确认接收，客户端按游标消费。
- 订阅断开时显示“实时通知未连接”，API 轮询继续工作。
- 主任务核验实际 Coolify 的 Webhook 认证能力；不得未验证就宣称有内置 HMAC 签名或完整重试保证。
- 获取用户确认后配置测试通知；不通过故意停止生产服务或制造故障验收。

**验收：** 重复、乱序、未知事件、无效来源、多实例相同资源 ID、客户端离线重连均通过；正常连接时事件到达客户端无需等待下一次 API 定时轮询；无推送配置时不影响基础功能。

### M4：后续全流程贯通（另行选择 CI 数据源）

- 在用户实际使用的 CI 中先选一个数据源，关联提交 → 构建/测试运行 → 产物 → 部署 → 运行/访问事件。
- 合并为统一项目时间线，保留每个阶段的事实来源与标识。
- 判断发布后出现异常时，只表述时间关联，未经证据不自动归因于该提交。

本阶段不在当前通知切片中顺带实现，也不要求用户迁移现有 CI/Coolify。

## 7. 安全与持续监控边界

- 沿用应用自有会话，不读取系统钥匙串或保存 Coolify 登录密码；只读 API Token 不进入白板、Git、导出、通知正文或普通日志。
- Webhook 接收与桌面订阅使用各自必要的认证；不复用 Coolify 管理 Token 作为接收口密钥。
- 外部载荷限制体积、验证结构，文本转义；不直接渲染原始 HTML、执行载荷命令或自动打开载荷 URL。日志/任务输出可能含敏感信息，默认只保存白名单摘要。
- 不提供部署、重启、停止、删除、回滚等写操作；查看事实和导航优先。
- Webhook 接收服务保存的是事件，不等于持续探测器。Coolify 自身停机、未发送的事件、独立域名可用性仍需外部持续监控兜底；是否接入外部监控在后续单独确认。
- 不新增云端白板同步、完整日志平台、媒体协作、额外供应商抽象或未经需要的依赖。
