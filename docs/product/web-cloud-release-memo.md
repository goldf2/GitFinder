# 开发备忘：Web 端、用户数据云同步与在线发布更新

日期：2026-08-31
状态：桌面更新客户端与发布产物流程已进入验证；云同步与生产发布部署仍未完成。

## 1. 产品方向

GitFinder 增加 Web 端，让用户通过账号在不同设备访问白板和相关资料，并建立在线发布更新的能力。采用“桌面端 + Web 端 + 云端服务”，延续现有白板视觉、关系模型和稳定资源身份，不依赖 Xiangshu Panel。

| 部分 | 职责 |
| --- | --- |
| 桌面端 | 本地目录与仓库扫描、Git 操作、代码定位、离线白板编辑；连接云端同步用户选定的内容 |
| Web 端 | 登录后查看和编辑白板、资源关系、备注、待办及素材；没有本地副本的资源仍正常显示 |
| 云端服务 | 账号与访问隔离、白板数据与素材保存、修订与备份、同步接口；提供独立的版本下载和更新分发能力 |

网页界面本身不等于云端持久保存；需有经过身份验证的后端与存储。优先复用共享数据模型、白板样式与交互，再将依赖 Electron 的文件、窗口、凭据与 Git 能力分离到各端适配层，不从零重写整个产品。

## 2. 当前基础与缺口

以记录时源码 `2.0.0-alpha.36` 为基线，不据此推断用户安装版已经同步。

- 已有：桌面白板、资源关联、本地白板项目文件夹和素材、`.gfb` ZIP 文件包。文件包继续用于携带、导入导出和备份，不以整包互相覆盖作为在线同步协议。
- 已有规划：[关系白板云同步边界](cloud-whiteboard-sync.md)，尚未实现账号和跨设备云同步。
- 已有更新客户端：打包应用默认使用 OakTech Alpha 发布目录，包含检查、发布页、下载进度、下载确认和重启安装流程。完成生产发布前仍需上传同版 macOS/Windows 产物与更新清单，并通过签名和旧版到新版安装验收。
- `server.js` 是默认监听本机回环地址的 Git 工具服务，不是多用户公网后端；不能直接将其开放公网来承载账号与用户数据。

## 3. 数据保存与同步边界

### 可进入云端

- 仅用户主动启用同步的白板：名称、说明、节点、关系类型与方向、群组、布局、折叠状态、别名、备注、待办及提醒配置。
- 项目、仓库与部署的非敏感稳定引用；各端显示名称不改变源资源身份。
- 用户确认同步的图片、媒体和附件。白板数据与素材分开管理，素材使用稳定引用，不依赖本机绝对路径。
- 云端修订记录和可恢复的备份；账号之间隔离，具体权限范围和保留策略实施前确定。

### 不随白板自动上传

- 本地仓库源码、目录树、绝对路径、目录授权、文件操作历史。
- Coolify API Token、Cookie、密码、SSH 私钥或任何可恢复凭据；不读取系统钥匙串。
- 仅“引用”而未复制进白板项目的外部文件。上传其内容需要用户另行选择，不因开启同步就自动收集。

登录由各客户端自己的账号会话管理；第三方数据源凭据与 GitFinder 登录会话分开，不进入白板、Git、日志或导出。换设备后以稳定身份重新关联当地目录；外部引用或本地资源缺失时保留占位、关系与说明，并允许重新关联。

### 一致性要求

- 本地优先：离线编辑可保存，联网后同步。
- 首次同步显示本地与云端差异；使用修订号或 ETag 检测并发修改，不用最后上传者无条件覆盖另一端。
- 冲突时保留双方内容并提供选择；删除保留同步删除标记，防止离线设备恢复已删除内容。
- 保存应明确显示本地已保存、同步中、云端已保存、失败或冲突，不能只显示笼统的“已保存”。

## 4. Web 上的 Coolify 状态

继续保留桌面直接只读连接 Coolify 的能力。Web 展示分两种层级，不能混淆：

1. **同步快照（可选后续切片）**：桌面将经字段筛选的观测快照同步给 Web，必须显示来源与最近同步时间。电脑关闭后显示的是历史快照，不是实时监控。该切片需补充既有云同步边界并独立确认，不属于首期白板文档同步。
2. **云端实时读取（后续另行授权）**：如果要求电脑关闭后 Web 仍持续刷新，需常在线的只读连接器及独立授权、凭据管理和运行配置，不能自动复制桌面 Token。直接读取 Coolify，不复制 Panel。

云端 Webhook 接收只验证、保存和转发事件，不等于持续探测器。运行健康、最近部署结果、HTTP 检测与数据源同步状态保持分别表示；未知仍为未知。与[全流程可视化与通知方案](delivery-observability-notifications-plan.md)衔接，但不将其中未实现的能力记为已交付。

## 5. 在线发布更新

### Web 版本发布

- 通过服务端发布新版；有未保存编辑时提示保存并刷新，不强制刷新丢失内容。
- 版本发布不覆盖用户数据库或素材；数据结构变化需有兼容和迁移方案，发布回退与数据恢复分别考虑。

### 桌面版本更新

- 复用现有 `electron-updater`，补齐发布源、平台与架构对应的安装包、更新元数据和发布流程。
- 当前统一发布流程见 [GitFinder 2 在线更新发布说明](../online-update-publishing.md)。
- OakTech 网页后台的发布记录管理版本、下载 URL、发布时间和更新说明，并原子生成 `latest*.yml`；桌面端不依赖后台管理 API 或动态产品页。
- 分离 Alpha/测试与稳定通道；发布说明、下载进度、错误提示和用户确认流程可见。
- 更新前保存白板；验证更新包完整性与来源。正式发布需完善签名；macOS 自动更新依赖签名条件，不能把当前开发签名包当作完整正式升级方案。
- 先做版本下载页及新版本提示，再完成 macOS/Windows 实际安装版的下载、重启升级与用户数据保留验收。发布更新不需要等待 Web 白板完整实现。
- 桌面仍交付本地应用包，不通过加载带本地文件权限的远程网页来替代应用升级。

技术参考（2026-08-31 核对，实施时按实际依赖版本复核）：[electron-builder 自动更新](https://www.electron.build/docs/features/auto-update/)、[Electron 更新指南](https://www.electronjs.org/docs/latest/tutorial/updates)。

## 6. 分期与最小验收

### W1：账号与一个白板的跨端闭环

账号登录 → 桌面选择一个白板和图片启用同步 → Web 打开并编辑 → 桌面取回修改。

验收：

- 同一用户在桌面与 Web 看到一致的节点、连线、布局、备注、待办和图片。
- 不同账号不能读取或修改彼此的白板及素材。
- 离线修改、双端并发修改和删除重连不会静默丢失数据或恢复已删除内容。
- 检查实际上传内容，不含本地源码、绝对路径和数据源凭据；未授权外部文件不上传。
- 另一台设备没有对应目录时仍显示白板，完成重新关联后可从桌面定位本地代码。

### U1：独立推进版本分发

先提供版本下载及更新提示，再接通现有更新器。验收必须在 macOS/Windows 安装版完成从旧版到新版的升级，确认取消/失败可继续使用、重启后版本正确且用户数据保留；构建成功或下载成功不能代替升级验收。

### W2：按需要扩展

多白板资源库、修订恢复和更多素材类型；随后再评估部署快照、云端实时连接器及事件订阅。首期不默认加入多人实时协同、公开分享或完整云端 Git 操作。

## 7. 实施前待定事项

- 服务域名、部署位置、账号开放范围及登录方式。
- 数据库、素材存储、容量与备份/保留策略。
- 发布托管位置、测试与稳定通道，以及签名条件。
- 是否需要电脑离线时仍获取实时部署状态；若需要，另行确认连接器和授权边界。

本备忘不授权上传现有用户数据、创建生产凭据或部署服务器。打包客户端的更新检查以实际发布目录和签名验收为准。
